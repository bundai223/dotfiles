# 2026-08-04 Neovim起動エラー復旧（セッション記録）

## 発生していたメッセージ

起動時に以下が出ていた。

```
Failed to source '/home/nishimura/.local/share/nvim/lazy/rainbow-delimiters.nvim/plugin/rainbow-delimiters.lua'
... module 'rainbow-delimiters.strategy.global.current' not found
```

## 診断結果

調査の過程で、独立した4つの問題が積み重なっていることが分かった。

### 1. rainbow-delimiters.nvim の作業ツリー破損

`~/.local/share/nvim/lazy/rainbow-delimiters.nvim` のgit作業ツリーが不整合だった。
`git status` で削除22ファイル・変更5ファイル。`lua/rainbow-delimiters/strategy/global/`
ディレクトリごと消えている一方、それを `require` する `strategy/global.lua` は
HEAD（`011d98e` / v0.8.0-27, 2025-02-12）のまま残っていた。

ディスク上の `.gitignore` / `.gitmodules` にはHEADには無いSPDXヘッダや
`.luals/addons` サブモジュール定義が入っており、新旧のファイルが混在していた。
チェックアウトが途中で中断したものと見られる。

### 2. treesitterパーサとクエリのバージョン不整合

`rainbow-delimiters` を復元すると、次に以下が出た。

```
Query error at 74:3. Invalid field name "operator": operator: _ @operator)
```

`nvim-treesitter` は `main` ブランチ（`61df849`, 2026-07-26）でクエリは新しいのに、
実際に読まれていた `lua.so` は `~/.local/share/nvim/lazy/nvim-treesitter/parser/` に
ある2026-04-22ビルドで、`operator` フィールドを持っていなかった。

この `parser/` `parser-info/` は旧 `master` ブランチ時代の遺物。`main` ブランチの
設定では `install_dir = stdpath("data") .. "/site"` を指定しており、
本来の配置先である `~/.local/share/nvim/site/parser/` は空だった。
パーサ262個のビルド日付は2024-02〜2026-04に散らばっていて、全て古かった。

### 3. lazy.nvim が nvim 同梱パーサを rtp から落としていた

旧パーサを退避すると、今度は `Parser could not be created for buffer 1 and
language "lua"` になった。nvim同梱の `/usr/local/lib/nvim/parser/lua.so` は
`operator` フィールドを持っており正常なのに、runtimepath に入っていなかった。

lazy.nvim (`lua/lazy/core/config.lua`) は rtp をリセットする際、libdirを

```lua
local lib = vim.fn.fnamemodify(vim.v.progpath, ":p:h:h") .. "/lib"
lib = vim.uv.fs_stat(lib .. "64") and (lib .. "64") or lib
lib = lib .. "/nvim"
```

で決めている。この環境は `/usr/local/lib64` が存在する一方でnvimのパーサは
`/usr/local/lib/nvim` にあるため、`lib64` 側と誤判定され同梱パーサが丸ごと
rtpから消えていた。従来は旧パーサ群が肩代わりしていたため表面化していなかった。

### 4. lua_ls の設定テーブルが変換不能

上記を直すと、次は以下が出た。

```
vim.schedule callback: .../vim/lsp/client.lua:853: Invalid 'data': Cannot convert given Lua table
```

`nvim_exec_autocmds` をラップして特定したところ、`lua_ls` の
`workspace/didChangeConfiguration` の params が原因だった。

```lua
library = {
  [vim.fn.expand("$VIMRUNTIME/lua")] = true,
  [vim.fn.expand("$VIMRUNTIME/lua/vim/lsp")] = true,
  "${3rd}/luv/library",
}
```

配列部とハッシュ部が混在したテーブルはnvimがautocmdの `data` へ変換できない。

## tree-sitter CLI の導入で判明したこと

`nvim-treesitter` の `main` ブランチはパーサのビルドに `tree-sitter build` を使い、
`lua/nvim-treesitter/health.lua` の `TREE_SITTER_MIN_VER` は `0.26.1` を要求する。
入っていたのは `cookbooks/rust` の `.default-cargo-crates` 経由で入った 0.20.8 で、
`build` サブコマンドが無かった。

公式READMEが案内する `cargo binstall tree-sitter-cli` は実行自体は2.5秒で成功するが、
取得されるprebuiltバイナリは **GLIBC 2.39** を要求する。この環境は
Ubuntu 22.04 / GLIBC 2.35 のため実行できなかった。0.26.1〜0.26.11 の
`tree-sitter-linux-x64.gz` を全て確認したが、いずれもGLIBC 2.39要求だった。

`cargo binstall --strategies compile` はソースビルドへ切り替わるものの
`--install-path` を受け付けないため、配置先を指定できなかった。
結局 `cargo install --locked --root ~/.local tree-sitter-cli` でビルドした（約5分24秒）。

ビルドには新しいRustが必要で、asdfの `rust` が2024年当時の `1.76.0` に
ピンされたままだったため `1.97.1` へ更新した。`cookbooks/rust` の既定は
`latest` なので、ピンが古いまま取り残されていた状態だった。

## 実施内容

- `rainbow-delimiters.nvim` を `git restore .` でHEADへ復元した。
- 旧パーサ群（262個, 202MB）を
  `~/.local/share/nvim/nvim-treesitter-legacy-backup/` へ退避した。
- `cookbooks/tree-sitter/` を新設し、`roles/base` から読み込むようにした。
  `cookbooks/rust/files/.default-cargo-crates` からは `tree-sitter-cli` を外した。
- asdfの `rust` を `1.97.1` へ更新し、`tree-sitter-cli 0.26.11` を
  `~/.local/bin` へビルドした。asdf側の古い `tree-sitter` バイナリとshimは削除した
  （asdfのshimは `/usr/local/bin` や `~/.local/bin` よりPATHで先に来るため）。
- `plugins.lua` の `lazy.setup` に `performance.rtp.paths` を追加し、
  nvim同梱パーサのディレクトリを明示的にrtpへ戻した。
- `mason-lspconfig.lua` の `workspace.library` を配列形式へ統一した。
- 主要言語24個のパーサを `~/.local/share/nvim/site/parser/` へ入れ直した。

  `:TSInstall` する運用とした。バックアップは
  `~/.local/share/nvim/nvim-treesitter-legacy-backup/` に残してある。

  ダウンロードから進まない。`:TSInstall` + `sleep` で回避した。

## 追記: 作業ツリー破損の真因と再発

`~/.gitconfig` を開くと別のエラーが出た。

```
rainbow-delimiters/lib.lua:190: attempt to index local 'parser' (a nil value)
```

### 再現しない理由

ヘッドレスでは再現しなかった。`rainbow-delimiters.nvim` は
`indent-blankline.nvim` の依存として `VimEnter` でロードされるため、
短時間のヘッドレス起動では当該のFileType autocmdが登録されていなかった。
`Lazy! load` で明示的にロードして初めて再現した。

### 原因

`gitconfig` は言語 `git_config` に対応するが、パーサを入れていなかった。
nvimはある時点から、パーサが無いとき `vim.treesitter.get_parser` が
エラーではなく **nilを返す** ようになった（neovim の commit fd1e019）。
復元したv0.8.0-27（2025-02-12）はこの変更前で、nilをそのまま
`parser:register_cbs` に渡していた。

v0.12.0 では該当箇所にコメント付きでガードが入っている。

### 作業ツリー破損の真因

`Lazy! update` を実行すると、checkoutが次のエラーで中断した。

```
fatal: not a git repository: ../../../.git/modules/.luals/addons/busted
fatal: could not reset submodule index
```

さらにプラグインを消してクリーンに入れ直すと、今度は

```
error: The following untracked working tree files would be overwritten by checkout:
	test/bin/busted  test/bin/lua  test/bin/nvim
```

`lazy-lock.json` は旧コミット `011d98e` を固定していた。新しいバージョンでは
`test/bin` がサブモジュールになっているが、旧コミットでは同じパスが通常ファイルで
追跡されている。lazyがロック先へ戻そうとするとこの衝突でcheckoutが中断し、
**作業ツリーだけ書き換わった中途半端な状態が残る**。これがセッション冒頭で見つけた
「新旧ファイル混在」の正体だった。つまり同じ操作をすれば何度でも再発する。

### 実施内容

- プラグインディレクトリを削除してクリーンに再インストールした
  （`v0.12.0-21-g012f148`）。`lazy-lock.json` も同コミットへ更新された。
- `git_config` / `gitignore` / `gitattributes` / `git_rebase` パーサを追加した
  （計28個）。
- パーサの有無を跨いで（gitconfig / 拡張子不明 / markdown）エラーが出ないことを
  確認した。

### その他の画面上のメッセージ

- `client.supports_method is deprecated` — `nvim-lightbulb` と `trouble.nvim` が
  旧形式のドット呼び出しをしている。`:checkhealth vim.deprecated` は
  実行時にしか検出しないためOKと出る。動作影響は無い。
- `E471: Argument required` — `:TSInstall` は `nargs='+'` なので引数なしで
  実行するとこれになる。`:TSUpdate` は `nargs='*'` なので該当しない。
- `[nvim-treesitter] warning: skipping unsupported language: *` — 言語名として
  リテラル `*` が渡された場合の警告。上記と併せて手動実行によるものと見られる。

### 補足

作業中、稼働していたnvim（PID 58511）が `~/.gitconfig` 用に作っていた
swapfileを削除した。バッファとファイル本体には影響しないが、そのセッションが
異常終了した場合の復旧はできなくなった。
