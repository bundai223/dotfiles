# モデル別役割分担体制の導入

現在のリポジトリに、大きめのフィーチャを自律遂行するための 3 役体制を導入する:

| 役割 | 担当 | 責務 |
|---|---|---|
| オーケストレータ | メインセッション（上位モデル） | 設計・タスク分解・タスク票作成・diff レビュー・メトリクス判定 |
| impl-sonnet | サブエージェント（model: sonnet 固定） | タスク票どおりの実装とユニットテストのみ |
| verify-runner | サブエージェント | テスト・検証の実行と定型報告のみ。コード修正禁止 |

原型は 2ndSystem の 003 精度向上遂行（2026-07-17 完遂、SC 全 PASS・イテレーション 1 回で収束）で
実証済み。**実装者と検証者を分離**し、**オーケストレータはプロダクションコードを書かない**のが骨子。

## モード判定

1. `.claude/agents/impl-sonnet.md` が**無い** → 「初回導入」（下記すべて）
2. 既に**ある** → 「フィーチャ追加」（§3 の orchestration.md 生成のみ）

## 前提チェック（初回導入）

1. git リポジトリであること（`git rev-parse --show-toplevel`）。違えば中止して報告
2. `.claude/agents/impl-sonnet.md` / `verify-runner.md` が既存なら**上書きせず**現状を報告して指示を仰ぐ
3. 対象リポジトリを調査して次を把握する（生成物に埋め込むため）:
   - 言語・テストランナー・リンタと実行コマンド（例: `.venv/bin/python -m pytest` / `ruff check .`。
     venv の有無、`cd` が必要なサブディレクトリに注意）
   - 依存ライブラリの追加可否ポリシー（CLAUDE.md や pyproject.toml / package.json から）
   - 設計文書の置き場所（specs/ / docs/ など）
   - コミットメッセージの言語慣例（`git log` を見る）

## 生成するもの（初回導入）

テンプレの丸写しではなく、**調査結果でプロジェクトに合わせて書き起こす**こと。

### 1. `.claude/agents/impl-sonnet.md` — 実装専任エージェント

frontmatter: `name: impl-sonnet` / `model: sonnet` / `tools: Read, Edit, Write, Bash, Grep, Glob`。
description には「タスク票を受けて実装する。設計判断はしない。実装委譲時は必ずこのエージェントを
使うこと（MUST USE for implementation tasks）」を必ず含める（オーケストレータの自動選択に効く）。

本文に必ず含める要素:

- リポジトリルートの絶対パスと、コマンド実行位置の規約
- **入力（タスク票）の前提**: タスクID / 対象ファイル / 関数・クラスとシグネチャ /
  参照すべき設計文書 / 満たすべきテスト / 禁止事項が渡される。
  **不足・矛盾があれば実装せず、何が不足かを報告して終了する**
- **厳守事項**:
  - タスク票の範囲だけを実装。無関係なリファクタリング・整形・コメント追加をしない
  - 設計変更が必要と気づいたら実装せず、理由と代替案を報告して終了（設計判断はオーケストレータの責務）
  - 新規ライブラリ追加の可否と使用可能ライブラリ一覧（調査結果から具体的に列挙）
  - 再現性の規約（乱数シード・現在時刻・環境依存値の扱い。プロジェクトに要件があれば）
  - 既存コードのスタイル（型ヒント・命名・docstring 等）に合わせる
- **完了条件**: 変更対象のテストとリンタを自分で実行してから、
  「変更ファイル一覧 / 実装の要点 3 行以内 / テスト結果 / 設計上の懸念（なければ『なし』）」の
  定型で簡潔に報告（コード全文の貼り付け禁止。git diff で確認できる前提）

### 2. `.claude/agents/verify-runner.md` — 検証専任エージェント

frontmatter: `name: verify-runner` / `model: sonnet` / `tools: Bash, Read, Grep, Glob`
（**Edit/Write を与えない** — 検証者にコードを直させないための構造的ガード）。
description に「フェーズ Checkpoint とイテレーション終了時の検証に必ずこのエージェントを使うこと。
コードの修正・実装は一切行わない」を含める。

本文に必ず含める要素:

- 検証レベル **unit**（テスト+リンタのみ）と **full**（実データ実行・再現性・メトリクス抽出まで）を
  オーケストレータが指定する
- full の手順はプロジェクトの受け入れ基準に合わせて書く（実行コマンド、`mktemp -d` での
  出力分離、同一条件 2 回実行 + `diff -r` での再現性確認、メトリクスの抽出元ファイル）
- **報告フォーマット**を定型で固定する（受け入れ基準 1 行 1 項目で
  `SC-xxx <名称>: <実測値> / 目標 <条件> → PASS|FAIL`、pytest/ruff 行、特記事項）。
  ログ全文の貼り付け禁止
- 「**判定をよく見せるための読み替え・条件緩和はしない。数字はファイルにある値をそのまま報告する**」を明記

### 3. `specs/<feature>/orchestration.md` — 運用規約（フィーチャごと）

対象フィーチャが決まっている場合のみ生成（未定なら §4 のテンプレ配置だけ行う）。
このファイルが**そのゴール遂行の運用の正**。必ず含める章:

1. **役割分担（厳守）** — オーケストレータは「プロダクションコード・テストコードを自分で
   書いてはならない。例外は 1〜2 行のタイポ修正のみ」。impl-sonnet は 1 タスク = 1 起動、
   **対象ファイルが重ならないタスクのみ並列**、同一ファイルは直列（該当タスク列を具体的に列挙）。
   verify-runner はフェーズ Checkpoint（unit）とイテレーション終了時（full）
2. **タスク票の書式** — タスクID / 対象ファイル / 実装内容（シグネチャ）/ 参照 / 満たすべきテスト /
   禁止事項。「曖昧さを実装エージェントに持ち込ませない。設計判断はタスク票を書く前に決める」
3. **進行手順** — tasks.md（進行台帳）のフェーズ順、成果は毎回 git diff レビュー、
   Checkpoint ごとに verify-runner、論理単位ごとに commit（push の可否・コミット言語も明記）
4. **受け入れ基準** — SC-001〜 の形式で、実行コマンドと数値目標を明記（ゴール状態の定義）
5. **改善イテレーション規約** — 1 イテレーション = 仮説 → 変更（委譲）→ 計測 → progress.md に記録。
   調整してよいパラメータを列挙。progress.md の記録形式
   （`仮説 / 変更 / 結果（before→after の数値）/ 判断（継続・方針転換・打ち切り）`）
6. **ガードレール（達成の偽装禁止）** — **評価条件・判定しきい値を動かさない**（動かしてよいのは
   手法側のみ）、禁止操作（git push・main マージ・データ削除など）、既存互換の維持
7. **停止条件** — イテレーション上限（既定 5 回）と頭打ち判定（2 回連続改善なし）。
   打ち切り時は progress.md に最終分析（到達値 / 構造的な壁の分析 / 残る選択肢）を書いて報告
8. **起動方法** — キックオフプロンプト（「orchestration.md を読み、規約に従って tasks.md の
   Phase 1 から遂行。実装は impl-sonnet、検証は verify-runner」）と `/goal` 文
   （「SC 全 PASS で commit 済み、**または**第 7 節の停止条件により最終分析が完成し報告済み」——
   打ち切りも goal 達成に含めるのが重要。無限反復を防ぐ）
