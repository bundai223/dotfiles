# runbook

Issue を受け取った瞬間から PR がマージ可能になるまでを、以下の 3 フェーズで進める。**フェーズを飛ばして直接コードを書き始めてはならない**。

## トリガー

以下のいずれかに該当したら本 skill を起動する。

- Issue URL（`https://github.com/.../issues/\d+` など）を渡された
- 「issue #123 を始めて」「この issue やって」「実装進めて」など、実装着手の指示を受けた
- 「PR まで作って」など、Issue から PR までの一気通貫を求められた

## 状態ファイル（3-file discipline）

作業ディレクトリ直下に以下の 3 ファイルを置く。全フェーズを通してこの 3 ファイルが唯一の共有状態。

| ファイル | 役割 | 書き手 |
|---|---|---|
| `plan.md` | 要件・設計方針・受入基準を人間が読める形で定義 | Phase 1 で作成、以降は不変が原則 |
| `todos.md` | 実装タスクの分解と進捗（`- [ ]` / `- [x]`） | 全フェーズで更新 |
| `changes.md` | 何を変えたか（PR 本文のドラフト） | Phase 2 以降で書き足す |

PR 作成時にはこの 3 ファイルすべてが揃っていることを必須とする。

## Phase 0: セットアップ（worktree の作成）

Phase 1 に入る前に、作業用の git worktree を切る。以降のファイル編集は**すべてこの worktree 内**で行い、メインチェックアウト（main を刺しているワークツリー）でファイルを書き換えない。

```bash
# <n> は Issue 番号、<slug> は短い英語スラッグ
git worktree add .claude/worktrees/<n>-<slug> -b feature/<n>-<slug>
```

- `plan.md` / `todos.md` / `changes.md` の 3 ファイルもこの worktree 内に置く
- Edit / Write ツールへ渡すパスは **worktree 内の絶対パス**（`/…/.claude/worktrees/<n>-<slug>/…`）を使う
- PR マージ後は `git worktree remove .claude/worktrees/<n>-<slug>` で片付ける

## Phase 1: 計画

1. Issue 本文を取得して要件を抽出する
2. `plan.md` を作成する（下記の節を必ず含める）
   - **目的**: この Issue が何を解決するか
   - **要件**: 満たすべき機能・非機能要件
   - **設計方針**: 採用するアプローチと却下した選択肢
   - **受入基準**: 完了とみなす条件（テスト観点を含む）
   - **影響範囲**: 変更するファイル・モジュール
3. `todos.md` に実装タスクを `- [ ]` で列挙する
4. **ユーザーに `plan.md` と `todos.md` を提示して承認を得る**。承認前に Phase 2 に進んではならない

## Phase 2: 実装 / テスト / レビュー

以下を **Agent ツールで並列起動** する（1 メッセージ内で複数 tool use を送る）。

| 役割 | 何をやるか |
|---|---|
| implement | `todos.md` のタスクを順に実装、進捗を `- [x]` に更新 |
| test | 受入基準を満たすテストを追加、既存テストが通ることも確認 |
| review | 実装結果を正確性・セキュリティ・パフォーマンス・可読性の観点でレビュー |

レビュー指摘があれば implement / test を再度呼んで対応する。全ての受入基準が満たされ、レビューが通るまで繰り返す。

`changes.md` にはこのフェーズを通して「何を変えたか」を書き足していく（差分の要約ではなく、意図と設計判断）。

## Phase 3: PR 作成

1. 3 ファイル（`plan.md` / `todos.md` / `changes.md`）が揃っていることを確認
2. PR 本文には `changes.md` の内容をベースに以下を含める
   - 概要（1〜3 行）
   - 変更点の要約
   - テスト観点
   - スクリーンショット（UI 変更がある場合）
3. PR 作成後、Issue との紐付け（`Closes #N`）を PR 本文の footer に入れる

## ガードレール

- **禁止**: Issue URL を受け取って本 skill を経由せずに実装を始めること
- **禁止**: `plan.md` のユーザー承認前に Phase 2 に進むこと
- **禁止**: 3 ファイルのうちどれかが欠けた状態で PR を作成すること
- **禁止**: worktree を作らずにメインチェックアウト側でファイルを書き換えること
- **推奨**: PR は 500 行以内。超える場合は Phase 1 に戻って分割を検討する

## フォールバック

sub-agent が利用不能な環境（Agent ツールなし、または対象エージェント未登録）では、Claude 単体で implement / test / review の役割を頭の中で切り替えて順次実行する。フェーズ構造と 3 ファイル規約は維持する。
