# 0001: lazy.nvimの遅延ロードを考慮した二層テストを行う

- ステータス: Accepted
- 日付: 2026-07-11

## 背景

このリポジトリのNeovim設定は、lazy.nvimの `event`、`ft`、`cmd`、`keys` などを
利用してプラグインを遅延ロードしています。そのため、Neovimを起動してすぐ終了する
ヘッドレステストと `:checkhealth` だけでは、実際の編集操作で初めてロードされる
プラグインのエラーを検出できません。

一方、テスト時に全プラグインを強制ロードするだけでは、本来のロード条件、依存関係、
ロード順序の不具合が隠れる可能性があります。プラグイン更新と設定変更を安全に行うには、
設定単体の健全性と実際の利用経路の両方を検証する必要があります。

## 決定

Neovimのプラグイン検証を、次の二層に分けます。

### 1. 全ロードテスト

lazy.nvimを通じて管理対象プラグインを明示的にロードし、各プラグイン本体と
設定モジュールがロード可能であることを確認します。このテストでは、遅延ロードされる
ため通常の起動確認に現れないLuaエラー、依存関係不足、削除されたAPIの利用を検出します。

### 2. シナリオテスト

プラグインを強制ロードせず、本来の条件からロードされることを確認します。少なくとも
次の経路を代表シナリオとして扱います。

- `BufReadPre`、`BufEnter`、`InsertEnter`、`CmdlineEnter`、`VimEnter`、`VeryLazy`
- Lua、Ruby、TypeScript、Markdownなど、日常的に利用する代表的なFileType
- プラグインが定義するコマンド
- プラグインのロード契機として登録されたキーマップ
- LSP、補完、Treesitter、フォーマットなどの主要な編集フロー

各テストは終了コードだけでなく、Lua例外、`vim.v.errmsg`、`:messages`、通知、lazy.nvimの
ロード状態を診断レポートへ収集します。非同期処理については、対象イベントの発火後に
完了条件または妥当なタイムアウトを設けます。

テストは次の段階で実行します。

1. 初期起動と `:checkhealth`
2. 全ロードテスト
3. シナリオテスト
4. 変更対象機能の対話的な確認

プラグイン更新は、この検証基盤を用意し、現在の `lazy-lock.json` をリポジトリで追跡して
更新前後を比較できる状態にしてから実施します。

## 影響

- 初期起動だけでは見つからない遅延ロード後の障害を検出できます。
- 強制ロードでは隠れるロード条件とロード順序の障害も検出できます。
- プラグインの追加や遅延ロード条件の変更時に、対応するシナリオの追加が必要です。
- すべての操作を網羅するのではなく、日常的な編集フローと変更対象を優先するため、
  対話的な確認は引き続き必要です。
- テスト時間が増えるため、短い起動テストと詳細なプラグインテストを個別に実行可能な
  構成にします。
